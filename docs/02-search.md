# 搜索增强：结果条数 / 触底翻页 / 切换页面保留结果

在 `jm/src/pages/SearchPage.tsx` 上实现，随同一份 APK 交付（与暗色模式、圆角玻璃、主题色、导出功能共存）。
产物与安装方式见 [`README.md`](./README.md)。

---

## 一、先说一个约束

后端搜索接口 `api_search` 只接受 `search_query` / `sort` / `page` 三个参数（见 `src-tauri/src/lib.rs:3737`），**服务端每页返回条数是固定的，不能指定**。

所以「可以指定多少结果」没法实现成"每次请求 N 条"，而是实现成 **每次展示 N 条**：后台按服务端分页把结果累积起来，前端按你选的粒度一批一批放出来。这也正好让「触底翻页」变成一个自然的分批追加，而不是把整页内容替换掉。

最终行为：**选好每批条数 → 滚到底自动放出下一批 → 服务端当前页放完了就自动去取下一页 → 直到结果全部加载完。**

## 二、三个需求的落点

### 1. 指定结果数量 —— 「每次加载 N 条」

- 搜索条件区新增下拉：`10 / 20 / 30 / 50 条`，默认 20，选择结果存 `localStorage["jm_search_batch_size"]`
- 首批只放出 N 条；每次触底或点「加载更多」再放出 N 条
- 缓冲里还有数据时不发请求，所以切粒度、连续加载都是瞬时的
- 头部信息条实时显示 `共 X 条 · 已加载 Y · 第 P 页`

### 2. 划到最底部自动翻页

- 结果列表末尾放了一个 1px 的哨兵节点，用 `IntersectionObserver`（`rootMargin: 400px`，即提前一屏触发）监听
- 触发时优先放出缓冲区里的下一批；缓冲区空了（服务端当前页已放完）才去请求下一页（`page+1`）
- 详细判断在 `loadMore()`：缓冲优先 → 否则请求下一页 → 新条目去重后追加 → 按批放出

处理了两个容易出问题的点：

- **观察者回调与请求完成的竞态**：IntersectionObserver 的"离开视口"通知可能晚于请求结束后的 effect，导致一次触底连加载两批。所以触发时**重新实测哨兵几何位置**（`sentinelInView()`）而不是相信可能过期的标志位。
- **搜索结果会漂移**：服务端两次请求之间榜单可能变动，第 2 页可能重复第 1 页的条目。追加时按 AID 去重；若连续 2 页都没有新条目（或已加载数达到 `total`）就判定到底，避免无限请求。

底部还有状态行：加载中转圈 / `已经到底了 · 共 N 条` / `继续下滑自动加载下一批（每次 N 条）`。

### 3. 切到别的界面保存搜索结果

会话状态（关键词、排序、每批条数、已累积结果、已放出条数、已加载页数、是否到底、**滚动位置**）整体缓存：

- **内存**：`memoryState` 模块级变量，应用内切页返回是瞬时的，**不会重新请求**
- **localStorage**（`jm_search_state_v1`）：冷启动/重载也能恢复，条目上限 400 条以免占满配额
- **URL** 同步保留 `?q=&sort=`（`replace`，不污染历史），深链/刷新仍可用

滚动位置的恢复有两个坑，都处理了：

1. 卸载时读 `window.scrollY` 会被浏览器**夹到新页面的高度**（新页面更短 → 读到 0）。改用 `useLayoutEffect` 的清理函数——它在 DOM 变更的同一同步任务里执行，浏览器还没重算布局，此时读到的仍是离开时的真实位置。
2. React StrictMode 会"挂载 → 卸载 → 再挂载"地双跑 effect，一次性 guard 会被第一次消耗掉、`requestAnimationFrame` 也被清理取消。所以恢复逻辑写成可重入的，并且把 `scrollYRef` 预置为缓存值、恢复前**静音滚动监听**，任何人都无法把记忆的位置冲成 0。

另外「清空结果」会同时清掉结果与缓存，避免下次进来还看到旧搜索。

## 三、UI 变化

- 条件区第一行：关键词输入框（占满整行）+ 搜索按钮
- 第二行：排序方式 + **每次加载**
- 第三行：**加载更多** + **清空结果** + 状态文字
- 原先的「上一页 / 下一页」按钮**已移除**：在累积式列表里它们语义不清（已经滑过的内容没必要再"回页"），改为「加载更多」+ 触底自动加载，位置信息移到头部信息条

> 顺带修掉一个自己引入又踩到的坑：如果把输入框单独放一行、把「搜索」按钮放到下一行，**搜索历史下拉会盖住「搜索」按钮**导致点不到（e2e 直接卡死在那次 click 上）。所以主操作按钮必须留在输入框同一行；同时搜索提交后自动收起下拉。

## 四、测试

新增 `e2e/search.spec.ts`（4 个用例）：

| 用例 | 断言要点 |
| --- | --- |
| 每次加载条数决定每批展示的结果数量 | 默认首批恰好 20 条；点「加载更多」→ 40；切到 10 条再加载 → 50；**这三次都没有新增请求**（吃缓冲区）；头部显示 `共 120 条 · 已加载 50` |
| 划到最底部自动加载下一批，直到全部加载完 | 首批 20 → 触底自动到 40 → 再触底到 45（总数）；出现「已经到底了」；再触底数量不变、请求数恰好 3 次（不空转）；**重载页面后仍恢复 45 条且 0 次请求** |
| 切到别的页面再回来，搜索条件、结果与滚动位置都保留 | 关键词、20 条结果、滚动位置都还在；`api_search` 调用次数**不变**（证明没重新请求）；继续「加载更多」仍从缓冲区取，也不发请求 |
| 清空结果后不再保留上一次搜索 | 清空后 0 条 + 暂无结果；切页返回仍是空的 |

同时改进了测试基础设施：`e2e/support/tauriMock.ts` 的 `api_search` 原先忽略 `page`、永远返回全量，现在支持 `searchPageSize` 并真的按页切片——否则「翻页/分批」这类逻辑根本测不出来。既有 IME 搜索用例不受影响。
