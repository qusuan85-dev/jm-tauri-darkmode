## 一、全站圆角

和颜色一样走「单点 token」而不是逐个组件改：`jm/tailwind.config.cjs` 里重映射了 Tailwind 的圆角尺度。

| 尺度 | 原来 | 现在 | 主要用在 |
| --- | --- | --- | --- |
| `rounded-sm` | 2px | 6px | 小标签 |
| `rounded` | 4px | 8px | 内嵌小块 |
| `rounded-md` | 6px | **12px** | 按钮、输入框、下拉、列表行 |
| `rounded-lg` | 8px | **16px** | 卡片、面板 |
| `rounded-xl/2xl` | 12/16px | 20/24px | 弹层、悬浮导航栏 |

实测断言：卡片 16px、控件 12px、悬浮栏 24px（`e2e/appearance.spec.ts`）。

## 二、液态玻璃

用在**底部悬浮导航栏**和**各类弹层**上（下拉、搜索历史、提示气泡、Toast、扫描弹窗、阅读菜单面板、阅读器信息气泡），按你的选择没有铺到全站卡片上 —— 大面积 backdrop-filter 在 WebView 里既费性能也压对比度。

实现是 `src/index.css` 里三个可复用类：

- `.glass` — 半透明 surface + `backdrop-filter: blur(18px) saturate(180%)` + 顶部高光内阴影 + 外投影 + 白色细边，浅深两套 alpha（浅色 0.72、深色 0.62）
- `.glass-nav` — 更实一点（+0.12 alpha），因为导航栏要承载小字号文字
- `.glass-scrim` — 阅读器里压在图片上的深色气泡

几个细节：

- 底部导航从「贴边整条」改成**悬浮圆角胶囊**（左右留 12px、距底 8px），页面底部预留空间从 5rem 提到 5.5rem；有一条断言专门验证**页面最后一张卡片不会被玻璃栏挡住**
- 用 `@supports not (backdrop-filter: …)` 回退成近乎不透明，避免老 WebView 上变成"半透明脏底"
- 玻璃效果只在内容穿过它时才看得出来，所以测试里是滚动到中途截图验证的

## 三、主题色切换

设置页「外观」卡片里新增 7 个色板：**蓝 / 紫 / 青 / 绿 / 橙 / 粉 / 默认灰**（默认灰保留原来的单色观感）。

- 浅色模式：深色填充 + 白字；深色模式：亮色填充 + 近黑字。每个色都是按对比度挑的（深色下文字对比度都 > 7:1，浅色下 > 4.5:1），不会出现"选了橙色就看不清字"
- 生效范围：主按钮、选中/激活态胶囊、链接、复选框/滑块（`accent-color`）、焦点环、侧边栏选中项
- 实现上最关键的一条规则：项目里所有"主按钮/选中态"都是 `bg-zinc-900 text-white`，所以**一条 `html .bg-zinc-900.text-white` 就接管了全部主操作**，包括 hover/active 的 `hover:bg-zinc-800`、`active:bg-zinc-950`
- 选择存在 `localStorage["jm_accent"]`，并写进 `<html data-accent>`；`index.html` 的首帧内联脚本也会应用它，冷启动不会先闪一下蓝色
- 默认是**蓝**；想回到原来的单色，点最后一个「默认」即可

## 四、导出到目录 + PDF

入口在**漫画详情页的「导出」按钮**（在「一键缓存」旁边）。**没有动现有的一键缓存**和它的 2GB 清理策略，这是新增的独立流程。

### 导出内容（可多选）

- 解密原图（按章节分文件夹，页序按文件名数字排序，保留原始格式）
- 每章一个 PDF
- 整本合并 PDF

### 目标目录

| 方式 | 位置 | 权限 |
| --- | --- | --- |
| 默认位置 | `Android/data/com.aa.jm/files/JM`（桌面端为「下载/JM」） | 不需要任何权限，文件管理器可见 |
| 自定义 | 系统目录选择器选的任意文件夹（SAF） | 选一次持久授权，之后一直用；可「清除」 |

自定义目录的写入路径值得说一下：Android 11+ 里 SAF 目录**只能通过系统的 Document API 写**，Rust 的普通文件 API 是写不进去的。所以流程是 **Rust 先把整本导出到暂存目录 → 原生桥（Kotlin `DocumentFile`）把每个文件流式拷进所选文件夹**。拷贝走的是原生流，不经过 JS，几百 MB 的合并 PDF 也不会把内存顶爆。

### 目录结构

```
JM/
└── 漫画名/
    ├── 001-第一话/
    │   ├── 0001.jpg
    │   └── 0002.jpg
    ├── 001-第一话.pdf
    ├── 002-第二话/
    ├── 002-第二话.pdf
    └── 漫画名.pdf          ← 勾选"整本合并"时才有
```

### 进度与取消

Rust 侧边下边发 `export-progress` 事件：先「准备 N/M 章」（解析每章页表与分割参数），再逐张图片推进，自定义目录时还有一段「正在复制到所选目录 k/n」。面板上实时显示，**取消**复用阅读器的 cancel registry（`api_read_cancel` + `export-*` key），下载/写文件/复制每一步都会检查取消标记。

### PDF 是怎么生成的

自己写了一个**流式 JPEG→PDF 写出器**（`src-tauri/src/pdf.rs`），没有引入 PDF 库，原因有三：不往 Android 构建里加新依赖、内存恒定（整本合并几百页也不会把图片都堆在内存里）、JPEG 以 `/DCTDecode` **原样嵌入不重新编码**，画质无损、体积也不膨胀。

- 页宽按 A4（595pt），页高按图片比例 —— 普通漫画页接近 A4，长条 webtoon 自动变成对应长度的长页（超过 14400pt 会等比缩回上限）
- 非 JPEG（PNG/WebP）先用已有的 `image` crate 转一次 JPEG
- 灰度/CMYK JPEG 会按分量数写对应的 ColorSpace

**验证**：写了一个独立 harness（不链接 tauri）生成 3 页样例与 120 页大文件，再用**真实 Chromium 的 PDF 查看器渲染确认**（页数 `1 / 3`、缩略图、长条页比例都正确），截图见 `screenshots/pdf-*.png`。

## 真机反馈修复记录

第一版装机后反馈了两个问题，已定位并修复：

### 1. 底部导航「阅读」按钮点了没反应

`阅读` 那一项是展开菜单的入口（在线收藏 / 本地收藏 / 浏览记录）。我把底部栏改成悬浮圆角胶囊时加了 `overflow-hidden`（本意是让子项背景不溢出圆角），结果**把向上弹出的菜单整个裁掉了** —— 菜单其实渲染了，但被父元素裁没，看起来就像个废按钮。

修复：去掉 `overflow-hidden`，改成给每个子项自己加 `rounded-xl` 与内边距（视觉一致且不裁剪），并加了回归测试 —— 这条测试我特地反向验证过：把 `overflow-hidden` 加回去它就失败。

### 2. 导出失败（图片和 PDF 都失败）

**根因找到了**：`api_chapter` 返回的 `images` 是**裸文件名**（如 `00001.jpg`），前端是先 `normalizeImgUrl(文件名, 章节ID)` 拼成完整 URL 再交给下载接口的；我在 Rust 里直接把裸文件名当 URL 去请求，于是**每一张都请求失败** —— 图片和 PDF 用的是同一批字节，所以两者一起挂。这也解释了为什么"图片和 PDF 都失败"而不是某个单独失败。

修复：把 `imgBase` 从网页层传进导出命令，在 Rust 里按同样的规则拼 URL；并在准备阶段做一次校验，一旦拼出来的不是 http(s) 地址就立刻报「图片地址无效（图片域名：…）」而不是静默失败 N 张。

顺带查出的其它问题一并修了：

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| 同上（裸文件名当 URL） | **图片与 PDF 全部失败** | 传 `imgBase` 并在 Rust 内拼完整 URL（`{base}/media/photos/{chapterId}/{文件名}`，绝对地址与 `/` 开头的情况也按前端规则处理） |
| `sanitize_path_component` 只保留 ASCII | 所有中文标题被过滤成 `unknown`，**不同漫画导出到同一目录会互相覆盖** | 保留非 ASCII（中日文正常），只剔除路径非法字符，并把 `.`/`..` 归一化，防止路径穿越 |
| 没有任何文件名长度限制 | 长标题超过 Android 的 255 字节上限时 `create_dir_all`/`File::create` 直接失败（CJK 每字 3 字节，80 多字就超） | 按**字节**截断到 120 并附短哈希，保证既不超限又不重名 |
| 章节 `id`/`title` 按严格 `String` 反序列化 | 后端若返回数字 id 或非字符串标题，整个命令参数解析失败 → 图片和 PDF 全部失败 | 改为宽松接收任意 JSON 值再转字符串 |
| 单章接口失败直接 `?` 冒泡 | 一个章节取不到就把整本导出打断 | 单章失败只跳过该章并记录原因，其余继续；全失败才报错并带上首个原因 |
| 错误信息很笼统 | 只提示"导出失败"，没法定位 | 现在带**步骤 + 具体路径 + 系统错误**（如「创建 PDF 失败：/…/001-第一话.pdf：…」），并**常驻在导出面板**里（不再只是一闪而过的提示条），同时写进应用日志 |
| PDF 一页都没成功时 | 留下一个 0 页的空 PDF 坏文件 | 自动删除并计入失败数 |
| 目标目录不可写 | 导出到一半才失败 | 开始前先做一次写入探测，失败立刻报出具体路径 |

> 我还验证过 `image` 的 JPEG 编码器对带 alpha 的图（透明 PNG/WebP）会自动转 RGB，不是失败原因；解密函数与现有可用路径完全一致。

**为什么这个 bug 没被测出来**：URL 拼装写在 `lib.rs` 里，而这个 crate 的测试二进制在 Windows 上链接 WebView2 后无法启动。所以我把这类纯逻辑抽到了独立模块 `src-tauri/src/paths.rs`（无 Tauri 依赖），并用一个独立 harness 跑它的单元测试 —— 现在有一条 `bare_file_names_get_the_cdn_prefix` 专门盯住这个坑。

**如果你再试还是失败**：现在面板里会显示具体原因（形如「创建 PDF 失败：<路径>：<系统错误>」），把那行发我即可精确定位；应用日志里也有 `[tauri][export] ... failed` 记录。

### 顺带修的测试稳定性问题

- 导出面板的进度断言原先是被章节列表按钮"误命中"通过的（真机上事件是异步来的，mock 却是同步发的，导致前端监听器还没注册事件就发完了）—— mock 改成带延迟发事件，断言收紧到进度行本身
- 上游那条 `local favorites scan can be cancelled mid-run` 在并发下偶发失败（扫描延迟 220ms 太短，可能还没点到"取消"就结束了），调到 900ms

修复后 e2e **27 个用例连续 4 次全绿**。

### 3. 下载/导出的图片是错位条带（分块数算错）

第二版装机后反馈：**导出的图片是横向错位的条带**（在 WPS 里打开能看到画面被切成一条条、上下接不上），而**应用内阅读是正常的**。

**根因**：禁漫的图是"横向切成 N 条再打乱"存的，N 由 `md5(章节ID + 文件名)` 的最后一个十六进制字符决定。这个**文件名不含扩展名**：

```
md5("147450600001")        -> N = 12   ← 正确
md5("147450600001.webp")   -> N = 4    ← 我导出时算的
```

前端阅读路径里的 `pictureNameFromPath()` 是 `base.split(".")[0]`，**本来就剥掉了扩展名**，所以阅读一直正常；而我在导出里用了 `picture_name_of()`（保留扩展名）去算 N，于是**大部分页的条数算错** —— N 错意味着每条的高度也错，重新拼接后就变成错位条带。

这也解释了为什么"阅读好好的、只有下载的有问题"：两条路径共用同一个 Rust 解密函数，唯一的差别就是喂进去的文件名。

**验证（不是猜的）**：我拿真实章节（album `1474506`，共 70 页）下载了前 12 页，对每一页穷举所有可能的条数（2/4/…/22）各拼一次，用"相邻行像素差"打分（拼对了接缝最平滑），得到的最佳条数**12/12 页全部等于不含扩展名的算法结果**，而不含 vs 含扩展名两套算法只在 3 页上偶然一致。随后又把参考实现（[JMComic-Crawler-Python](https://github.com/hect0x7/JMComic-Crawler-Python) 的 `JmImageTool.decode_and_save`，它的实体里把文件名和扩展名分开存为 `img_file_name` / `img_file_suffix`）逐行抄成 Python 跑了一遍：**我们的分块搬运与参考实现逐字节一致**。

| 页 | 含扩展名（错的） | 不含扩展名（对的） |
| --- | --- | --- |
| 00001.webp | 4 | 12 |
| 00002.webp | 4 | 4 |
| 00003.webp | 4 | 2 |
| 00004.webp | 2 | 14 |
| 00005.webp | 14 | 6 |
| 00006.webp | 6 | 10 |
| 00007.webp | 4 | 6 |
| 00008.webp | 2 | 8 |
| 00009.webp | 16 | 14 |
| 00010.webp | 4 | 4 |
| 00011.webp | 14 | 14 |
| 00012.webp | 8 | 6 |

修复后效果（左侧是修复前的下载文件，右侧是修复后）：`screenshots/uifix-descramble-before-after.png`

**修复**：把分块数的计算从 `lib.rs` 挪进纯逻辑模块 `paths.rs`，并在里面统一剥掉扩展名（`picture_stem_of()`），这样阅读路径（传 `00001`）和导出路径（传 `00001.webp`）必然得到同一个数 —— 不再依赖调用方自觉。

**回归测试**：`paths.rs` 里新增 `segmentation_num_matches_real_pages`，把那 12 页**实测出来的条数**固化成断言（含扩展名/不含扩展名必须一致、旧版本算法必须与它不同）。另外把解密函数从 `lib.rs` 挪进了同样无 Tauri 依赖的 `scramble.rs`，于是"拆条 → 拼回"这一步也能在本机跑测试了（三张真实页面 + 合成图的往返）：

```bash
cd jmwork/pathcheck && cargo test   # 11 passed（含 12 页真机数据向量）
cargo run --release                 # 真机端到端：3 张真实 WebP 走完整 Rust 解密链路
```

`cargo run` 的输出是这次最有力的证据 —— 它用**应用真正会用的解码器**（`image` 的 `png/jpeg/webp` 特性集）解开服务端下发的 WebP，再用**真正的 `descramble_image_bytes`** 试遍所有条数，选"接缝最少"的那个：

```
0001_00001.webp: best_num=12 computed=12 raw_tv=6.293 best_tv=5.745 runner_up=2 (6.388)
0004_00004.webp: best_num=14 computed=14 raw_tv=4.401 best_tv=3.972 runner_up=2 (4.461)
0006_00006.webp: best_num=10 computed=10 raw_tv=9.300 best_tv=8.952 runner_up=2 (9.379)
```
